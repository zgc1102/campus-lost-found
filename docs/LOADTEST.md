# 压测与容量说明

目标：证明“1 万人打开”和“200 人/分钟发布”时系统仍然可用，并给出可复现的数据。

---

## 一、怎么跑

本机（开发环境）：

```bash
python scripts/loadtest.py --base http://127.0.0.1:8000 --path / --requests 1000 --concurrency 100
```

线上（能正常解析域名时）：

```bash
python scripts/loadtest.py --base https://你的域名 --path / --requests 10000 --concurrency 500
```

本机 DNS 解析不了域名时，直连 Cloudflare 边缘 IP：

```bash
python scripts/loadtest.py --base https://shiguangli.work --path / --requests 300 --concurrency 30 --connect-ip 104.21.15.101
```

Windows 一键：双击项目里的 `压测.bat`。

输出示例：

```json
{
  "rps": 812.4,
  "ok": 9998,
  "failed": 2,
  "failRate": 0.02,
  "latencyMs": { "p50": 38, "p95": 210, "p99": 480 }
}
```

## 二、三个关键指标

| 指标 | 含义 | 及格线 |
|---|---|---|
| **失败率** | 打不开的比例 | < 1% |
| **p95** | 95% 的人多久打开 | < 1.5 秒 |
| **rps** | 每秒处理请求数 | 首页 ≥ 300 |

---

## 三、这套架构为什么能扛

```
用户 → Cloudflare（缓存静态资源）
     → Caddy（直接发 HTML/CSS/JS，压缩 + 长缓存）
     → Python（只处理 /api/*）
```

- 页面和静态文件**不经过 Python**，Python 只处理接口
- 接口有 ETag：内容没变返回 304，不重复传
- CDN 挡掉大部分重复请求，源站压力降到 1/10 以下

## 五、发布侧压测（可选）

发布接口会调用大模型，不适合用脚本狂刷（会产生费用）。建议用**限流 + 队列**的设计说明，而不是压测数字：

- 每设备 3 条/分钟
- 发布立即返回「审核中」，后台队列处理
- 队列深度、平均审核耗时在管理端可见

如果确实要测，用 10 个不同 owner 各发 1 条，观察是否全部收下、审核是否在 30 秒内完成。

---

## 六、注意事项

- 压测会消耗真实带宽，线上跑一次即可，别反复刷
- Cloudflare 免费版对单 IP 有速率限制，压测时可能被挑战，属正常
- 不要把压测脚本指向别人的网站
